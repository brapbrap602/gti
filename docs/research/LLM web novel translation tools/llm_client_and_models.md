# LLM client stack, OpenRouter features and model choice for batch zh->en translation (Oct 2026)

Research date: 2026-10-20. Library metadata comes from the PyPI JSON API, fetched today. Model prices come from the live OpenRouter `GET /api/v1/models` listing, also fetched today (468 models).

## Q1. Which client should make the calls: openai SDK, the official OpenRouter SDK, or httpx directly?

### Takeaway
There is now an official, Apache-2.0 `openrouter` Python SDK (1.3.69, released 2026-10-20). It is generated by Speakeasy, and its README has no retries or error-handling section. The `openai` SDK (3.35.1) pointed at OpenRouter's base_url is the most mature sync client. It has built-in retries that honor 429s, but it now depends on `httpx2` rather than `httpx`. Plain `httpx` plus a retry library is the smallest option and exposes OpenRouter-specific fields (`provider`, `models`, `reasoning`, `usage.cost`) with no SDK typing in the way.

### Cited Findings
- `openrouter` 1.3.69 was uploaded 2026-10-20. Its summary reads "Official Python Client SDK for OpenRouter.", it is Apache-2.0, needs Python >=3.10, and depends on `httpcore>=1.0.9, httpx>=0.28.1, jsonpath-python>=1.0.6, pydantic<2.13,>=2.11.2`. — [PyPI openrouter](https://pypi.org/pypi/openrouter/json)
- Its README says "The OpenRouter Python SDK is stable as of v1.0". It is installed with `uv add openrouter`, the same client serves sync and async use, and the call is `chat.send`. — [PyPI openrouter](https://pypi.org/project/openrouter/); [PyPI org page, "Last released Aug 18, 2026" at search time](https://pypi.org/org/openrouter/)
- The README holds Speakeasy placeholders `<!-- No Retries [retries] -->`, `<!-- No Error Handling [errors] -->` and `<!-- No Custom HTTP Client [http-client] -->`. So there is no documented retry config. — [PyPI openrouter](https://pypi.org/pypi/openrouter/json)
- A separate Python port of `@openrouter/agent` was released on 2026-08-03. — [PyPI org openrouter](https://pypi.org/org/openrouter/)
- `openai` 3.35.1 was uploaded 2026-10-18. It is Apache-2.0, needs Python >=3.10, and depends on `anyio, httpx2<3,>=2.12.0, jiter, pydantic, sniffio, typing-extensions`. The README says it offers "both synchronous and asynchronous clients powered by HTTPX2". — [PyPI openai](https://pypi.org/pypi/openai/json)
- In the openai SDK, connection errors, 408, 409, 429 and >=500 "are all retried by default" (`max_retries` default 2, configurable per client or per request). Requests are retried only when the body can be resent safely, and stream consumption is not retried. — [PyPI openai README](https://pypi.org/project/openai/)
- `httpx` 0.28.1 (BSD-3) was released 2024-12-06 and has had no release since. Its dependencies are `anyio, certifi, httpcore==1.*, idna`. — [PyPI httpx](https://pypi.org/pypi/httpx/json)

### Inferences
- With the openai SDK, OpenRouter-only parameters (`provider`, `models`, `reasoning`, `session_id`) have to go through `extra_body`. Cost is read from `usage.cost`, which is an extra field on the typed usage model. This works but is weakly typed.
- `openai` 3.x moved to `httpx2`, while `litellm` (and therefore DSPy) still requires `openai<3.0.0`. Mixing them in one uv workspace forces openai 2.x. Pick one family.
- For a sync pipeline with background threads, the smallest dependable stack is either of these:
  - (a) `httpx` plus `tenacity` or `stamina`, behind a small `ChatModel` protocol, with a fake implementation for tests.
  - (b) `openai` with `max_retries` set, behind the same protocol.
  Option (a) gives full control over `Retry-After`, the 402 `limit_source` and mid-stream error handling, with three small dependencies.
- The official `openrouter` SDK is typed for OpenRouter fields. Two things make it a weaker choice for unattended batch jobs: the pin `pydantic<2.13` (which may clash with other packages) and the absence of documented retries.

### Gaps
- I could not confirm whether the `openrouter` SDK has any retry or backoff logic that the README leaves out. Read its source (Speakeasy `RetryConfig` utilities) before relying on it.
- I did not test whether the openai 3.x typed models keep OpenRouter's extra `usage.cost`, `cost_details` and `cache_write_tokens` fields, though pydantic `extra=allow` is typical.

## Q2. litellm (as an SDK): features, weight, security history, cost tracking

### Takeaway
litellm is heavy and was hit by a serious supply-chain attack in March 2026. For a single-provider (OpenRouter) pipeline it adds risk and weight and gives nothing that OpenRouter's own `usage.cost` does not already provide.

### Cited Findings
- `litellm` 1.106.1 was uploaded 2026-10-20 (MIT, Python `<3.15,>=3.10`). Its core dependencies, even without extras, include `openai<3.0.0`, `tiktoken`, `tokenizers`, `huggingface-hub`, `boto3`, `aiohttp`, `httpx[http2]`, `jinja2`, `jsonschema`, `pydantic-settings`, `python-dotenv`, `pyyaml`, `click`, `filelock`, `fastuuid` and `importlib-metadata`. — [PyPI litellm JSON](https://pypi.org/pypi/litellm/json)
- In March 2026, the malicious versions 1.82.7 and 1.82.8 were published to PyPI with an infostealer:
  - 1.82.7 hid a base64 payload in the proxy server code.
  - 1.82.8 added `litellm_init.pth`, which runs at every interpreter start and passes pip hash checks because it is listed in RECORD.
  - The attack was attributed to "TeamPCP", following their compromise of the Trivy scanner.
  - Both versions were quarantined and the maintainer's credentials were rotated.
  - Reports put exfiltrations at about 500k, which BleepingComputer could not verify.
  — [BleepingComputer](https://bleepingcomputer.com/news/security/popular-litellm-pypi-package-compromised-in-teampcp-supply-chain-attack); [Snyk](https://snyk.io/de/articles/poisoned-security-scanner-backdooring-litellm/); [NetSPI](https://www.netspi.com/blog/executive-blog/ai-ml-pentesting/litellm-supply-chain-compromise/); [SecureLayer7](https://blog.securelayer7.net/pypi-litellm-supply-chain-attack/)
- The sources disagree on the entry point. One says a maintainer's GitHub account and CI/CD were compromised. Another says the attacker uploaded directly to PyPI with stolen credentials. — [BleepingComputer](https://bleepingcomputer.com/news/security/popular-litellm-pypi-package-compromised-in-teampcp-supply-chain-attack); [SecureLayer7](https://blog.securelayer7.net/pypi-litellm-supply-chain-attack/)
- DSPy 3.4.1 depends on `litellm>=1.65.8`, so it inherits the same exposure. — [PyPI dspy](https://pypi.org/pypi/dspy/json)

### Inferences
- litellm's cost tracking relies on its own price map. OpenRouter already returns the authoritative charged `cost` in every response (see Q4), so litellm's cost feature is redundant here.
- If litellm is used at all, pin an exact version with hashes in `uv.lock`. Its release cadence is near-daily (a release appeared on the day of this research), which widens the window for a bad release.

### Gaps
- I did not check whether litellm has had a CVE or incident after March 2026.

## Q3. Structured output and orchestration libraries: overkill or useful?

### Takeaway
None of these is needed. OpenRouter supports `response_format: json_schema` natively on most current models (390 of 468 list `structured_outputs`). A Pydantic model, `model_json_schema()` and `model_validate_json()` cover term extraction. Instructor (re-ask on validation failure) is the only one worth considering, and it brings a large dependency set.

- How OpenRouter structured outputs work:
  - The request takes `response_format: {type: "json_schema", json_schema: {name, strict, schema}}`. `strict: true` is enforced exactly only by providers with native strict mode.
  - Support is per endpoint, not per model, and requests to unsupported endpoints error.
  - Set `provider.require_parameters: true` to route only to endpoints that support the parameter.
  - The Response Healing plugin repairs invalid JSON for non-streaming json_schema requests.
  — [OpenRouter structured outputs](https://openrouter.ai/docs/features/structured-outputs)
- In the live model list, 390 of 468 models advertise `structured_outputs`. This covers every current DeepSeek V4.x, Qwen 3.7/3.8, Gemini 3.x Flash, Kimi K3/K2.6, GLM-5.3 (non-flashx/prime), Claude 5.x and GPT-5.6 entry. `z-ai/glm-5.3-prime`, `z-ai/glm-5.3-flashx` and `qwen/qwen3.7-flash` list only `response_format` (JSON mode), not `structured_outputs`. — [OpenRouter models API](https://openrouter.ai/api/v1/models)
- Instructor's main entry point is `instructor.from_provider("openai/...")` with `response_model=`. It "handles" retries and validation. — [PyPI instructor README](https://pypi.org/project/instructor/)

### Inferences
- Outlines and guidance do constrained decoding against local or open weights. Over a remote OpenRouter API they add nothing beyond `response_format`, so they are a poor fit.
- LangChain, DSPy and Marvin are frameworks (graphs, prompt optimisation, agent DB). They are overkill for "send a prompt, get text or JSON, record cost". DSPy also drags in litellm.
- pydantic-ai is good quality and has a built-in `TestModel`/`FunctionModel` for tests. But it is async-first (sync wrappers run an event loop), needs Python >=3.11, and pulls OpenTelemetry. That is acceptable but not minimal.
- Mirascope has the lightest core. It is still an abstraction layer you don't need for a single provider.
- The minimal plan: a Pydantic schema, `response_format` json_schema with `strict: true`, `provider.require_parameters: true`, then `model_validate_json`. On a validation error, retry once (optionally feeding back the error).

### Gaps
- I did not verify whether pydantic-ai 2.x ships a dedicated OpenRouter provider class, or whether instructor's `from_provider` accepts an `openrouter/` prefix. Both work with an OpenAI-compatible base_url in principle.
- I did not measure real-world schema-adherence rates per model on OpenRouter.

## Q4. OpenRouter platform features relevant to the job

### Takeaway
Every response now carries `usage.cost` (the actual charge) plus cached and reasoning token breakdowns, with no opt-in. Paid models have no platform request cap. Fallbacks are handled with `models` and `provider` routing. OpenRouter now has a native Batch API at about 50% price.

### Cited Findings
- **Usage accounting**
  - Every response includes `usage` with `cost` (the amount charged), `cost_details.upstream_inference_cost` (BYOK only), `prompt_tokens_details.cached_tokens`, `prompt_tokens_details.cache_write_tokens` and `completion_tokens_details.reasoning_tokens`.
  - `usage: {include: true}` and `stream_options.include_usage` are deprecated and have no effect.
  - Async lookup by generation `id` goes through the `/generation` endpoint.
  — [OpenRouter usage accounting](https://openrouter.ai/docs/use-cases/usage-accounting)
- **Rate limits**
  - Free (`:free`) models allow 20 RPM, and 50 requests/day, or 1000/day once at least 10 credits have been purchased.
  - Paid models have "no platform-level request cap", but provider limits still apply.
  - Extra keys or accounts don't raise limits.
  - Cloudflare blocks traffic that "dramatically exceed[s] reasonable usage".
  — [OpenRouter limits](https://openrouter.ai/docs/api-reference/limits)
- **Error handling**
  - 429 `rate_limit_exceeded` may come from the platform or the upstream provider (`error.metadata.provider_code`). Platform 429s carry `X-RateLimit-*` headers and sometimes `Retry-After`.
  - A limit hit mid-stream arrives as an SSE event with `finish_reason: "error"`.
  - 402 is split by `error.metadata.limit_source`:
    - `openrouter_in_flight_budget`: wait for `Retry-After`.
    - `openrouter_key_limit`: the key's credit limit is used up.
    - `openrouter_credits`: the balance is too low. `reason: weight_exceeds_budget` means a single request is too big.
  — [OpenRouter limits](https://openrouter.ai/docs/api-reference/limits)
- **Key/credits API**: `GET /api/v1/key` returns `limit`, `limit_remaining`, `limit_reset`, `usage`, `usage_daily`, `usage_weekly`, `usage_monthly`, `is_free_tier`, `free_model_daily_requests` and budgets (`rate_limit` is deprecated). — [OpenRouter limits](https://openrouter.ai/docs/api-reference/limits)
- **Provider routing**
  - The `provider` object takes `order`, `allow_fallbacks` (default true), `require_parameters` (default false), `data_collection` ("allow"/"deny"), `zdr`, `only`, `ignore`, `quantizations`, `sort` ("price", "throughput" or "latency"), and `max_price`.
  - A top-level `models` array gives ordered fallback models.
  — [OpenRouter provider routing](https://openrouter.ai/docs/features/provider-routing)
- **Prompt caching**

  | Provider | How it works | Write cost | Read cost | Notes |
  |---|---|---|---|---|
  | DeepSeek | Automatic | Same as input | 0.1x | |
  | Gemini 2.5+ | Implicit, free | Free (implicit) | 0.25x | Min 1024 tokens (Flash) or 4096 (Pro). Explicit `cache_control` has a 5-min TTL and uses only the last breakpoint. |
  | Qwen (Alibaba) | Explicit `cache_control` only | 1.25x | 0.1x | 5-min TTL |
  | Anthropic | `cache_control` | 1.25x (5-min), 2x (1-hour) | 0.1x | Up to 4 breakpoints |
  | Moonshot | Automatic | Free | 0.25x | |
  | OpenAI | Automatic | Explicit at 1.25x on GPT-5.6+ | 0.25-0.5x | Min 1024 tokens |

  Sticky routing keeps a model on the same provider after a cache hit and expires after 10 min idle. `session_id` (body or `x-session-id`) sets the routing key explicitly. — [OpenRouter prompt caching](https://openrouter.ai/docs/features/prompt-caching)
- **Reasoning**
  - `reasoning: {effort: max|xhigh|high|medium|low|minimal|none, max_tokens, exclude, enabled}`.
  - Reasoning tokens bill as output, even when excluded. They count against `max_tokens`, and if they exhaust it the response comes back with `finish_reason: "length"` and empty content, still billed.
  - Models flagged `mandatory` reject `effort: "none"`. Check `supported_efforts` and `mandatory` in `/api/v1/models`.
  - Gemini 3 maps effort to thinking levels, with "minimal" the lowest.
  — [OpenRouter reasoning tokens](https://openrouter.ai/docs/use-cases/reasoning-tokens)
- **ZDR**
  - `provider.zdr: true` routes only to ZDR endpoints. It can only add ZDR, never remove it.
  - Account-level ZDR can be set per model group.
  - OpenRouter does not retain prompts unless you opt in to logging.
  - In-memory provider caching is not counted as retention.
  — [OpenRouter ZDR](https://openrouter.ai/docs/features/zdr)
- **Batch API (it exists, correcting the brief's assumption)**
  - Endpoints: `POST /api/v1/batches`, `GET /api/v1/batches/:id` (results inline), `GET /api/v1/batches` (list) and `DELETE` (purge after completion).
  - Request: `{endpoint, model, requests:[{custom_id, body}]}`. `requests` must come last in the JSON or the API returns 400.
  - Supported endpoints: `/v1/chat/completions`, `/v1/responses`, `/v1/messages` and `/v1/embeddings`.
  - Completion window is `24h` only. Pricing is "typically" 50% of standard. Each batch runs on one provider (cheapest by default), and only `provider.only` and `provider.allow_fallbacks` are accepted.
  - Results are kept 30 days, and a `callback_url` webhook is available.
  - Streaming is rejected. On Google models every request in a batch must share one `response_format`.
  — [OpenRouter batch quickstart](https://openrouter.ai/docs/batch-quickstart)
- 76 `:batch` model variants are listed today. — [OpenRouter models API](https://openrouter.ai/api/v1/models)

### Inferences
- **Cost accounting:** store `usage.cost` and the token fields per call. No generation-stats lookup is needed for normal calls, and no client-side price table is needed.
- **Retry policy:**
  - 429 and 5xx: exponential backoff with jitter, honoring `Retry-After`.
  - 402 `in_flight_budget`: wait and retry.
  - 402 `key_limit` or `credits`: stop the job. This is not retryable.
  - Also treat a 200 with `finish_reason: "error"` or `"length"` (empty content) as retryable or failed.
- **Caching:** put the stable glossary and system prompt first and the chapter text last. DeepSeek and Gemini cache automatically. Qwen and Claude need `cache_control` markers. Set `session_id` per novel to keep sticky routing.
- **Batch API:** worth it for bulk backfills where a 24h turnaround is fine. Interactive or job-thread translation should use sync chat completions.

### Gaps
- I did not find a documented maximum batch size or a cancel endpoint, even though `cancelling` and `cancelled` statuses exist.
- The exact path for generation stats (`/api/v1/generation?id=`) is linked, but I did not open it.
- Throughput limits imposed by individual providers (for example DeepSeek's own RPM) are not documented on OpenRouter.

## Q5. Retry libraries

### Takeaway
Use `tenacity` (no dependencies, actively maintained), or `stamina` (a thin, opinionated tenacity wrapper with a test switch to turn retries off). Avoid `backoff`, which has not been released since 2022.

### Cited Findings
- `tenacity` 9.2.1, 2026-10-07, Apache-2.0, Python >=3.10, no dependencies. — [PyPI tenacity](https://pypi.org/pypi/tenacity/json)
- `stamina` 26.1.0, 2026-04-13, MIT, depends only on `tenacity`. It has "dedicated support for testing that allows to globally deactivate retries, or to limit the number of retries and to remove backoffs", plus structlog and logging integration. — [PyPI stamina](https://pypi.org/pypi/stamina/json)
- `backoff` 2.2.1 was last released 2022-10-05 (MIT). — [PyPI backoff](https://pypi.org/pypi/backoff/json)

### Inferences
- tenacity's `wait` can be a custom callable that reads `Retry-After` from the exception. stamina's `retry_context` or `on=` callable can do the same.
- stamina's global test switch fits the fake-model test setup.

### Gaps
- I did not verify whether stamina 26.x supports a backoff hook driven by `Retry-After`.

### Inferences
- A rough per-chapter cost, assuming about 3k Chinese chars ≈ 3-4k input tokens with a glossary and about 3-4k output tokens: DeepSeek V4.1 Flash, GLM-5.3-flash and MiMo flash come to roughly $0.001 per chapter or less. Gemini 3.8 Flash is about $0.02 per chapter. Thousands of chapters cost single-digit to tens of dollars on the cheap tiers.
- Reasoning tokens can dominate output cost on thinking models. For translation, set `reasoning.effort` low or none where the model allows it.
- Prices change frequently, and the `/models` figure reflects one default endpoint. Store `usage.cost` rather than computing cost from list prices.

### Gaps
- I found no 2026 public leaderboard ranking current models (DeepSeek V4, Qwen 3.8, Kimi K3, GLM-5.3) specifically on zh->en literary or web-novel quality. The DITING paper's per-model scores were not extracted.
- I did not check which providers serve each model (quantization, ZDR availability) on OpenRouter.
